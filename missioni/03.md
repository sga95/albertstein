# Missione 3: la pipeline

**Cosa ottieni:** capisci cosa succede tra il tuo commit e il sito online, e proteggi `main` da errori.

**Perché conta:** "CI/CD" è nelle offerte di lavoro anche per ruoli di rete e infrastruttura. Non devi costruirla, devi saper dire cosa fa e come si usa.

## Passi

1. Su Cloudflare, Workers & Pages → albertstein → Deployments. Ogni riga è un deploy. Apri quello dell'ultima missione: guarda "Build log" e quanto ha impiegato.
2. Rispondi per iscritto: perché il build log è quasi vuoto? (Suggerimento: il sito non ha un passaggio di build. Cosa cambierebbe se usassi un generatore statico?)
3. Su GitHub crea un branch chiamato `test-preview`, cambia qualcosa di visibile, fai push. Vai su Cloudflare: c'è un nuovo deploy di tipo "Preview" con un URL tipo `test-preview.albertstein.pages.dev`. Aprilo. Il sito vero non è cambiato.
4. Cancella il branch senza fare merge. Il preview sparisce dalla lista dei domini attivi.
5. Su GitHub: Settings → Branches → Add branch protection rule per `main`: richiedi una pull request prima del merge. Da ora niente commit diretti su main, nemmeno i tuoi.
6. Rompi il sito apposta: in un branch, cancella la parentesi graffa finale di `progress.json`. Apri la PR, guarda il preview: la barra non si carica. Correggi, la PR si aggiorna, il preview funziona. Merge.
7. Segna la missione 3 come fatta, con una pull request (ormai è obbligatoria).

## È fatta quando

- `main` è protetto e lo puoi dimostrare con uno screenshot delle regole.
- Sai dire a voce, in un minuto, il percorso commit → GitHub → Cloudflare → CDN → browser.
